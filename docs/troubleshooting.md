# Troubleshooting

| Symptom                                                   | What to check next                                                                                                                                                                                                                                                                          |
| --------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| npm cannot find the package                               | Build from this checkout or install its reviewed local tarball. The public registry returned 404 for this name on 2026-11-22. Name ownership and publication are pending.                                                                                                                   |
| Doctor cannot connect                                     | Start the MCP server first. Check its Streamable HTTP path, scheme and port. Use a literal loopback endpoint or explicitly allow the exact remote HTTPS URL. Credentials, query parameters, fragments and redirects are rejected. Authenticated endpoints are outside the current workflow. |
| A stdio executable fails during discovery                 | Check the JSON target shape, installed executable, working directory (the target file's directory) and arguments. Run the trusted server separately to inspect its own stderr. SDK negotiation may start a probe and session executable.                                                    |
| Doctor reports zero tools or calls                        | A tool-less server can be reachable. Discovery reports server hints and issues zero tools/call requests. To observe a real call, review an explicit suite, authorize the case, and run test.                                                                                                |
| The server returned success but CI exited 3               | Inspect the final state event and terminal attempt IDs. A response, final file, or timeout cannot prove that queued work is finished. Export the downstream effect and terminal ID in one coherent snapshot.                                                                                |
| A snapshot exists but the baseline is unavailable         | Initialize version 1 with an operations map and publish by atomic rename. Mark partial exports incomplete. With verify.maxAgeMs, use a UTC publishedAt timestamp, synchronize clocks and publish recent snapshots.                                                                          |
| An at-most-one contract fails                             | Inspect the actual committed records for the generated operation key. Decide whether that business operation needs deduplication. Repeated appends correctly create multiple effects unless the application requires otherwise.                                                             |
| The CLI was killed or a retry is withheld                 | Open the progress journal from stderr and follow the recovery procedure below. A completed suite produces a run directory with JSON and JUnit.                                                                                                                                              |
| Replaying a report reports historical or invalid evidence | Use the original report.json. Keep the case list, event order and complete evidence. Re-run a historical experiment on an isolated target if current proof is required.                                                                                                                     |

## Recover an interrupted run

1. Use the progress path printed on stderr when `test` started, or find `pending-*/progress.json` under the selected output directory. Run `mcp-reliability-kit journal "$PROGRESS_JSON" --json`. This offline command exits 3 for an incomplete run and 2 for unreadable or unsupported input.
2. Read `active.operationKey` and `active.possibleAttempts`. Search the authoritative transaction store and job queue for that operation and those attempt IDs. Compare committed effects, terminal jobs and any outstanding work. A recorded intent can precede transport delivery. A missing reply can follow a committed effect. Observation-only tools may lack any backend correlation.
3. Inspect completed case records as well. A process can die just after publishing the final pair of files. If the matching `run-<uuid>/report.json` exists, use `report` to inspect that suite. Older journals carry no in-flight identifiers. Preserve the evidence and reconcile ambiguous records with the service owner before authorizing another run.
