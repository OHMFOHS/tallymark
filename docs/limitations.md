# Limits of the evidence

- **Fault boundary.** The lost-response fault suppresses delivery after the SDK has received a reply. It exercises application retry logic with a known fault schedule. Wire-level disconnects, partial frames, transport resumption and server crashes are separate experiments.
- **Settlement.** A local snapshot can establish final state only to the extent that its producer observes committed effects and all outstanding work. A missing or incomplete projection yields INCONCLUSIVE. A producer that labels queued work terminal can generate a plausible green transcript before later effects occur. Attempt IDs establish correlation. They cannot establish the truth of the exporter. V1 assumes the isolated operation key covers all effects of interest. It cannot discover unrelated charges in an external system.
- **Protocol coverage.** The SDK handles current per-request negotiation and supported legacy handshakes. Tests cover current stdio, current Streamable HTTP and 2025-11-25 stdio and session-based Streamable HTTP (including session deletion). Legacy HTTP+SSE, authentication, tasks, interactive input, sampling and resumable streams are outside the tested surface. Discovery skips tools that explicitly require task-augmented execution. Tool calls that require interactive continuation stop with unknown outcome.
- **Cancellation.** A client timeout does not establish server-side receipt or rollback. The bundled fixture records cancellation independently and preserves the payment committed before it. An external timeout case with missing cancellation telemetry remains INCONCLUSIVE. Real deadlines can expire before dispatch under severe host load. The settlement check preserves the uncertainty. In the [Python Streamable HTTP experiment](http-cancellation.md), a running job committed after the cancelled request and client process had both ended.
- **Fixture durability.** A single local POSIX filesystem holds the synthetic ledger. A writer checks and appends receipts under an exclusive lock, flushes an atomic replacement and syncs the directory. A hard kill during a write can leave a lock file. Use a fresh fixture directory or verify all writers have stopped before recovering a standalone test ledger. The implementation models a local payment book; it makes no claim about distributed provider transactions.
- **Cleanup and permissions.** SDK auto negotiation can start the configured stdio executable twice, first in a disposable discovery process and then for the session. Startup actions must tolerate this, including for `list`. The SDK closes direct stdio children. Legacy Streamable HTTP sessions receive an explicit bounded DELETE on close. The runner removes its own fixture directories on normal completion and handled interruption. SIGKILL and machine failure can leave temporary directories. External services, state files, child-created daemons and irreversible payments are owned by the test operator. A trusted external executable runs with the permissions of the local user. Use a dedicated sandbox when testing third-party software.
- **Reproduction and privacy.** Synthetic fixture schedules and keys are reproducible. External keys are fresh for each run. Endpoint URLs, command arguments, verifier paths, raw replies, child stderr and tool argument values are omitted from evidence. Public scenario, target and tool identifiers are visible. Keep credentials out of those identifiers. A finite passing trace establishes only the declared bounds for that case.

- **Trust and isolation.** HTTP permissions grant a canonical endpoint URL; DNS and the host remain trusted. Executable targets also require `--allow-stdio`. A malicious local executable can exceed the resources of this process. Input and output schema checks for external servers run in fixed local subprocesses, each with a 96 MiB V8 old-space cap and a 1.5 s timeout. This cap covers the validator heap generation, not whole-process resident memory. Apply an OS sandbox and an outer job deadline when stronger isolation is required.

- **Independent implementations.** The Filesystem, Memory and Git reference servers share one upstream project. Two use the TypeScript SDK and Git uses Python. The checked-in evidence covers Filesystem stdio and loopback HTTP, and Memory/Git stdio. Read-only annotations, file contents, a graph row or a commit hash alone cannot identify every terminal invocation. A separate [Backburner experiment](backburner.md) supports one bounded positive result with a fixed SQLite worker and native job completion.
- **Interrupted reports.** The beta.2 journal records dispatch intent before each call. A kill can occur between that write and network delivery, or after a backend commit and before its reply. The offline journal reader reports every possible attempt for the active case. Look up both effects and terminal attempts at the authoritative backend before rerunning. Older journals omitted the active case. Directory metadata and host power loss have separate filesystem durability semantics. Only a complete report with the planned case list is eligible for the gate. Reports and journals are unsigned.
- **Visibility and isolation.** A complete, atomic export must include all side effects associated with terminal IDs. Polling can detect a regression only if it sees both snapshots. Reference experiments use dedicated disposable directories, local Git configuration, explicit allowlisted endpoints and exact packages. Directory separation is not an OS privilege boundary.

- **Doctor.** A successful diagnostic means protocol discovery succeeded. Zero tool calls, server hints and tool names do not establish whether any business operation is safe. A trusted executable can perform startup actions before discovery.
- **Freshness.** Export-age checks depend on synchronized clocks and an honest publication timestamp. The observer cannot measure unreported replication lag or prove that work reported terminal will never resume.
